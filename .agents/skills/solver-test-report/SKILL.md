# Solver test report

Explain what each scenario tested, what happened, why we think it happened, and the most useful first fix or experiment. Write for solvers who cannot access internal logs. Make the report understandable on its own. An error inventory followed by requests to check logs is not a completed investigation.

## Jupiter reports

For Jupiter, always produce only `{timestamp}_jupiter_solver_test_report_for_cow.md`. Open with the requested brief summary and specific praise for verified successes or recoveries, then focus on errors: quote rejections, failed orders or attempts, cleanup failures and missing evidence needed to investigate them. Do not create a separate solver report or add successful scenario sections, performance tables or coverage summaries. Group repeated errors with counts and affected tokens; keep exact errors, final outcomes and useful order links. State unknown ownership clearly. Aim for about 200 words, with compact error evidence if needed. This rule overrides the two-report, per-scenario, successful-example and comparison formats below for Jupiter; evidence checks still apply.

Always keep a Debug tool URL column for Jupiter errors. Link every failed order or cleanup action that has an order ID, even when shortening or grouping the report. For quote failures without an order ID, say "No order ID: quote failed before placement"; never invent a debug link or use a successful order as the failed request's link.

For requests that received no usable quote or failed before placement, include representative tokens, trade direction, order kind and requested amount. Use verified symbols and token links; keep a mint or scenario label when the symbol is uncertain. Give a short possible reason based on the saved error and available evidence, clearly labelled "Possible reason (unconfirmed)" unless verified. For repeated failures, group them but keep examples and affected row numbers. Separate the observed failure stage from its possible cause: `NoLiquidity` means the quote API returned no usable route for that request, not proof that Jupiter returned no quote, that the token has no liquidity, or that support is permanently absent. Explain missing order links and unknown ownership. If evidence doesn't support a specific cause, say "Cause unknown" rather than inventing one. Apply the same rule to other failures before placement, such as creation or validation errors, using their actual stage and message.

## Check the runs

1. Confirm the solver, environment, selected sessions and filename timestamp. Sessions are in `sessions/` at the repo root (`../sessions/` from `sim/`). Check metadata; a shared prefix alone does not confirm which runs belong.
2. Read `meta.json`, `report.md` or `report.html`, and `sim/scenario.csv` for the setup and test goal.
3. Check `sim/journal.jsonl` for placement, retries and cleanup; `orders.json` or `orders.csv` for final outcomes; and `txs.json` for settlement signatures. Check field names before querying.
4. Resolve uncertain counts or errors using selected records from `logs/settle_failures.txt`, `logs/creation_expired.txt` and `logs/competition.json`. Use compact queries, not full log dumps. Quote exact errors rather than generic report labels.

When reading Grafana, verify the data source matches the run's environment before querying containers. A `prod` simulator flag does not select a production Grafana data source. If queries return no records, inspect available data sources and check the order against the matching one before reporting missing logs. In this workspace, production VictoriaLogs uses `vm-auth-prod` and staging uses `vm-auth-staging`; verify these names still exist. Keep supplemental evidence when correcting an earlier query. Read the exact swap input, output, limits and shortfall before explaining "swap does not satisfy order"; check separate solved attempts and join driver failures by auction, solver and solution, rather than assuming all attempts had the same outcome.

Do not skip a Grafana or RPC read because it is slow or times out. Keep a running read pending and wait for its result, using short polling waits so progress updates remain possible. If the request itself times out, retry with a longer request timeout or a narrower query and wait again. Record which reads remain pending; do not call the investigation complete or replace them with a request for the solver to check logs. A deadline in automatic approval review means the command never started, not that Grafana or RPC failed. Follow the tool's retry limits, distinguish an explicit denial from a timeout and report any unresolved access blocker accurately. Never bypass an approval denial.

When permitted, a simple `curl` command can finish an existing log or RPC read if a helper cannot launch. Keep the long response timeout and temporary failure retries. Pass credentials through protected input or a temporary header file with mode `0600`, never through printed command arguments. Remove temporary credential files as soon as the reads finish. A public schema or decoder can support instruction decoding only when its discriminator and fields match the transaction; it does not by itself establish the historical deployed version or exact rounding.

Before concluding that credentials are missing, check the configured environment and existing project credential files, including `sim/.env`; `logs.load_credentials` checks only exported variables and the root `.env.<environment>`. Read only required keys into memory and never print secrets. Verify the data source through authenticated `/api/datasources`. With `logs.Logs.rows`, alias `_time` and `_msg` before selecting fields because the helper retains labels only. A full text search for an order ID can miss structured records; use structured order fields or a narrow time window and join by auction, solver and solution. Saved failure timestamps can be the start of settling rather than the time of the error. Use `Logs.rows` for supplemental reads; do not overwrite source exports with `fetch_logs`.

Use the selected completed reruns. Exclude superseded setup or configuration runs, but keep failures from selected runs. Ask if selection is unclear. Use the requested timestamp prefix when supplied, otherwise the test date as `YYYYMMDD`. Use metadata for the date inside the reports.

Read saved artifacts, existing live logs and chain data; write Markdown only. Do not stage changes automatically. Trades, scenario or infrastructure changes, PDFs, commits and publishing need a separate request.

## Use investigation agents

For a new report or substantive update with unexpected failures or an unmet feature goal, spawn investigation subagents with **medium reasoning effort**. Use one agent per solver when reporting several solvers; split a single solver only when its failure groups can be investigated independently. Give each agent the selected session paths, report paths and ownership constraints, not a proposed conclusion. Pass only the context it needs. A clean run needs a bounded review of feature goals and test limitations, not invented defects.

Each agent must investigate raw evidence, not just rewrite the existing diagnosis. Recover available original API/provider responses, joined driver/auction/solution records and failed transaction logs. Check the environment before querying logs. Use read-only RPC or existing debug evidence for failed signatures when available; inspect relevant integration code using exact error strings or known symbols when it helps locate the failed condition. Compare failed requests with useful successful controls, including amount, kind, account mode, timing and final outcome. Do not replay quotes, orders or transactions.

For each material failure group, return: affected scope; verified failure mechanism; our leading explanation and confidence; the evidence supporting it; the strongest alternative and counterevidence; the most likely component to inspect, separately from proven repair ownership; and one practical fix or experiment with the result that would confirm or reject the explanation. Quantify gaps where possible: token shortfall, fee deficit, transaction bytes, quote age, selection score, wave cutoff or blockhash lifetime. Do not invent measurements or impose a cause when the evidence cannot rank alternatives.

Agents may edit only their assigned reports when the coordinator assigns that ownership. Tell them they are not alone in the workspace and must preserve others' changes. Agents must not recursively delegate this same report assignment. The coordinator must review their reasoning against cited raw evidence, resolve conflicting conclusions and check report completeness before delivery. Do not present an agent's opinion as a verified fact merely because it came from a separate agent. If subagents cannot run, disclose that limit and perform the same investigation in the main agent.

## Investigate failure groups

Every report must attempt to explain each distinct failure group, including failed attempts on orders that later filled. Group by failing stage, exact error and relevant request pattern: token pair, sell versus exact buy, amount, native versus wrapped SOL, sponsored versus self-paid, wave or batch. Do not merge different programs or errors just because they share an API wrapper. Keep expected rejections and known and accepted limitations separate from unexpected failures. Work read-only; do not replay quotes, orders or transactions without authorization.

1. Count affected requests or distinct orders and failed attempts separately. Record final outcomes and all affected rows in the scenario evidence. Prioritize groups by blocked flows, unfilled orders and repeated retries; keep cleanup separate.
2. Inspect the original records for a representative failure from each group and any example that contradicts the suspected cause. Compare a nearby successful request only when its kind, direction, amount and account mode make it useful; state the differences. Check whether failure follows exact buys, smaller amounts, a wave cutoff or account mode before calling it a token-support problem.
3. For quotes, recover the request, API response and available driver/provider response using request IDs and timestamps. Check amount units, native SOL normalization, route availability, fee deductions, minimum trade sizes, response validation and rate limits only where evidence points to them. `NoLiquidity` alone identifies none of those causes. A previous run's diagnosis is context, not evidence of the current run's cause.
4. For candidate rejection or execution failure, join order, auction, solver and solution. Inspect the first failing instruction and its program logs, not just the outer `FailedToSubmit` or `SimulationFailed` wrapper. For Jupiter or other swaps, identify the instruction and swap mode from logs or a verified discriminator/schema, then retain quoted and actual input/output, signed limits, encoded threshold, slippage allowance, fees and shortfall. An exact-input route can fail its minimum output; an exact-output route can deliver all requested output and still fail its maximum input. `SlippageToleranceExceeded` alone does not identify which inequality failed. Distinguish either swap failure from a later payout transfer failure. Check integer rounding, whether driver simulation passed, whether execution landed, and whether cancellation happened first. State when a current public schema is only supporting evidence rather than a verified historical deployment. Do not decode a numeric error without a verified program mapping.
5. Give each group a short diagnosis inside its existing scenario evidence block. Explain the affected scope, confirmed failure, our opinion and confidence, a useful alternative, the first fix or experiment and ownership in short paragraphs. Explain why our leading explanation fits better than alternatives. Separate the immediate failure, underlying trigger, likely component and proven repair owner. Label hypotheses **Possible reason (unconfirmed)** and give a reason for the confidence level. When the underlying cause is unknown, say **Cause unknown** but retain any useful narrowing of the problem. List the checks actually completed and the exact missing response, request ID, auction/solution or failed transaction that prevents a stronger conclusion. Give a bounded experiment with a representative request or order, UTC time, values to compare and an expected result. “Check logs”, “investigate quoting” or a list of possible causes is insufficient. Recommend a concrete fix when the evidence supports it, otherwise name a conditional fix and the observation required before applying it.

Apply these diagnoses to both report scopes and Jupiter's errors-only report. Repeat shared solver and uncertain-ownership diagnoses in the CoW report; keep confirmed service-only findings out of the solver report. Put our leading explanation for the top 1–2 findings and its first fix or experiment in the TLDR and scenario summary without expanding the visible report into a troubleshooting log. “Could you compare these fields?” alone is not our opinion. Preserve detailed failure rows and links. If detailed evidence is unavailable, state that limit and the useful scoping result rather than inventing a cause or claiming the investigation is complete.

## Deliver a message with the report

Whenever you generate or update completed reports, also draft one copyable message per solver unless the user explicitly asks for reports only. Do not wait for a separate request for messages. Draft each message from the final reviewed report after checking its counts, diagnoses, ownership and links. Producing both report variants still means one message for that solver. Return the report file links and the accompanying messages together in the final reply. Keep the messages in chat, outside the report bodies, without creating extra message files. These are drafts for the user to share, not permission to send messages externally.

For Jupiter, keep the single CoW report file and accompany it with a clearly labelled internal CoW message only. Its message can include CoW issues because CoW is the recipient; do not create an external message to Jupiter by default. For other solvers, use the solver-facing filter below. Requests to rewrite messages alone can reuse the reviewed reports without regenerating them or repeating the investigation.

Open each message casually without naming the recipient: for example, "Hey, here are the results from your latest test run" or, after an actual rerun, "Hey, just reran the tests". Give the brief result and warm, specific praise for the strongest verified wins in 1-2 short sentences: batch sizes, completed bursts, direct matching or useful token coverage. Make the explanation friendly too, rather than adding only a cheerful greeting. Keep planned versus placed counts when that difference matters; say how many requests never reached placement and give their grouped reasons, separately from accepted orders that later expired or were cancelled. Add the standalone line "Here are some notable orders" before the flat bullet list. Use one issue per bullet in the format `- Short description: what happened and our quick take or useful first check. Order description (https://debug.barn.cow.fi/order/{uid}); another order description (https://debug.barn.cow.fi/order/{uid}).` Keep explanations to about 20-35 words before the example links, usually 1-2 short sentences. Use extra words only when they prevent a misleading explanation. Keep the numbers that make the failure clear; leave the full arithmetic and investigation history in the report's evidence blocks. State whether each example later filled, stayed cancelled or expired, usually in its link description. Shorten the explanation, not the useful examples.

Keep major outages and missing coverage in the opening as brief test context, even when the solver cannot fix them. State affected counts and what was not tested, without assuming the solver caused the outage. Keep detailed CoW troubleshooting internal. Only turn an issue into a solver action bullet when the reviewed evidence gives that solver a specific, useful check or change within its control. Before keeping a bullet, name the exact solver-produced record, route, amount, account list or decision it can inspect and explain how that would narrow the problem. Finding an error in a solver-labelled driver is not enough. Leave out CoW fee estimates and caps, misleading API errors, our request limits, order creation and blockhash handling, cancellation timing, simulator sizing and test setup when CoW must investigate those first. Do not keep them as "no action needed" updates or ask the solver to inspect internal CoW settings. For example, omit Grafiks CRCLx quote rejections until we know whether its route cost actually caused the driver's fee-budget failure.

Unknown repair ownership does not automatically make an issue useful to the solver. Keep a shared issue only when the evidence already identifies something specific in its submitted solution to check, such as a payment amount exceeding swap output or a route's encoded quote disagreeing with execution. Describe that check without calling it a confirmed solver defect. Detailed investigations of generic NoLiquidity responses, unexplained timeouts and missing engine responses stay internal until we can identify a solver-side question; their grouped counts still belong in test context when needed to explain missing placements or coverage. Adding "perhaps" or a speculative cause does not make a CoW issue actionable. Do not fill a short message with weak findings or unrelated successful orders. If nothing useful remains, give the result and praise without inventing an issue list. This filter applies to outgoing solver messages, not evidence retention: preserve the full failure records and ownership notes in the appropriate reports. Internal CoW messages, including Jupiter's internal message, still include issues CoW can act on.

Speak directly to the recipient: "your solver", "your quote" or "what you sent back", not "Asao's response" when writing to Asao. Write as if sending a friendly chat message, including in the explanations, not just the greeting. Offer suggestions rather than instructions, such as "so I'd perhaps start with..." or "you could have a look at...". Connect the suggestion to what happened with ordinary words such as "so". Do not add "perhaps" mechanically to every bullet. Avoid "let's check" when the recipient would do the investigation; use joint wording only for work we actually share. Prefer commas and full stops in explanations, keeping semicolons mainly for chaining order links.

Prefer "worked on retry" to "recovered", "swap's limit" to "encoded threshold" and "wasn't picked" to "lost ranking". Avoid labels such as "Priority fee budget rejection", "Slippage trigger unknown" and "Candidate generation gap", and awkward wording such as "whether the RPC node knew about it". Say plainly what failed and name the useful thing to inspect. Do not turn every bullet into a formal diagnosis followed by "We'd compare..." or a broad question such as "Could a direct match have worked after fees?". Give our observation and a gentle, specific suggestion instead of asking the recipient to work out what we mean. Read each explanation aloud; rewrite anything that sounds like an incident report or talks about the recipient as if they were absent.

Examples of the intended tone: "It worked on retry, so I'd perhaps start with how old that quote was." "The payment asked for more than the swap returned, so you could have a look at the payment amount in your solution." "These opposite SOL/USDC orders still went through separate swaps. I'd perhaps start with the fees on a direct match, to see if that explains it." These are wording examples, not default diagnoses; use each suggested check only when it fits the reviewed evidence and gives the solver a useful action. A question can suggest the first check, but must follow a useful observation or our supported opinion.

Keep our opinion clear without turning guesses into facts. Say "We think" or "We don't know yet" where needed. Do not replace the actual failure with vague phrases such as "too little room for price changes" or end with a list of possible fixes. Recommend changing amounts only when the evidence shows how the full order and fees stay within the user's limits. For failures without an order ID, explain why no Debug link exists and label any successful comparison. Reuse reviewed investigations for wording or example updates; repeat reads or delegate again only when a new question needs investigation.

Put each complete solver message in its own fenced plain text code block so the block's Copy button preserves the text. Include its short opening, "Here are some notable orders" and flat bullet list inside the block. Do not add Markdown formatting or escape characters inside it. Keep paragraphs and bullet items on one source line each.

Put a real `https://debug.barn.cow.fi/order/{uid}` link beside every finding or comparison that has an order ID; a local report or transaction link does not replace it. In messages and visible report prose, put each order description before its URL in parentheses and separate multiple examples with semicolons, such as `USDe cleanup, cancelled (https://debug.barn.cow.fi/order/{uid}); USDG buy, filled after a retry (https://debug.barn.cow.fi/order/{uid}).` Do not use arrows, Markdown links, square brackets, angle brackets or inline code around URLs. For a repeated issue, normally include 2-3 affected orders when available, choosing examples that show its spread across tokens, amounts, order kinds or outcomes. Cover distinct failure groups rather than linking several orders from one group and leaving another without evidence. Describe examples with tokens and useful details such as amount, small, large, sponsored, recovered, cancelled or expired. Do not mention CSV row numbers in messages, report summaries, visible scenario prose or their link descriptions; keep source row identifiers inside closed evidence blocks when needed for traceability. Do not add unrelated orders to reach a count; if only one relevant order exists, say so. Report the total affected scope separately so examples do not look like the full list. Put any remaining affected orders in the report's scenario evidence.

For failures before placement that pass the actionability filter, explicitly say no order was created, give the request and UTC time and label any linked comparison as a successful order. Never substitute a successful order for the failed request. If a record cannot be joined to an order, say that and give its request ID or auction/solution instead of attaching an unrelated Debug link. Add a failed transaction link when it helps prove the diagnosis. Questions may follow the diagnosis but must not replace it. Keep the requested friendly tone, leave CoW-only investigations in internal reports and messages, and carry forward known and accepted limitations without requesting fixes for them. Link positive findings and accepted limitations to representative orders when mentioning them too.

Use simple, informal English in reports and messages, as if sending a teammate a quick note. Say what happened and what we would check first in everyday words. Explain necessary technical terms briefly; keep exact program names and error codes in detailed evidence when the short message does not need them. Use plain ASCII punctuation, straight quotes and apostrophes, and normal hyphens. Write token pairs as "SOL to USDC" or "SOL/USDC". Do not use arrows, emojis, decorative separators, curly quotes or long dashes in reader-facing text. Preserve exact raw errors, identifiers and URLs in evidence. Keep the single label colon in message bullets and avoid extra colons or hyphenated expressions in the explanation. Put our opinion and the useful next step in the visible text, with detailed evidence inside the existing closed blocks.

## Count results

- **Filled / scheduled:** completed scenario trades / planned rows. Also count placed orders, failures before placement and expected rejections. Retries can create multiple orders for 1 row.
- **Total transactions:** distinct successful settlements for selected scenario orders. Exclude creation, funding, failed attempts and cleanup. Define this scope once.
- Include setup trades when they are scenario rows, and say so. Exclude cleanup from totals; keep its evidence in the relevant scenario.
- Use filled orders for timing. Check the source clock: placement to observed fill, creation to settlement block time, or scenario start to completion. Name both endpoints and whether polling delay is included. Use the same basis throughout; do not average scenario medians.
- Separate failed attempts from failed orders. Show when an order filled later. Deduplicate messages about the same attempt. A deadline warning after a failed submission does not prove a late solver response.

## Did the test achieve its goal?

Lead with a direct answer to the test goal: **achieved**, **not achieved**, or **inconclusive**. For example: “CoW was not achieved. Opposite orders settled through DEX swaps.” Put that answer before fill counts; avoid vague wording such as “no evidence of matching” when transactions show what happened. Use inconclusive when evidence is missing or our setup missed the target, and say why. Assign setup changes and reruns to the test team, not the solver. Fills alone do not prove that a feature worked.

- **Batching:** group orders by settlement signature and report batch sizes. Inspect swap instructions before claiming 1 swap, proportional payouts or a price guard. Link an example transaction.
- **CoW:** verify opposite orders shared an auction and matched directly without DEX swaps. Same direction batches are not CoW. A failed quote may block 1 pair while others remain testable. Treat unverified price guard explanations as hypotheses.
- **Throughput:** show wave counts and clearing times where useful. Separate creation failures from settlement limits. Bursts with pauses do not establish a sustained rate ceiling.
- **Tokens:** separate fixed input sells, exact output buys and expected rejections. A successful sell does not prove buy support. Check amounts and native SOL handling before treating `NoLiquidity` as a token issue.
- **Size:** measure the full serialized transaction, including signatures, against the 1232-byte limit and test target. Do not infer size from order count or earlier routes. Below-target transactions leave the limit test inconclusive.

Check solver participation in competition records, not DEX names. Decode custom numeric errors only when their program is known. Separate confirmed causes from possible explanations; missing evidence proves neither success nor failure.

Keep quoting, placing an order, accepting a solver solution and settling the trade separate. A quote or placed order does not prove the solver produced an accepted solution. A "swap does not satisfy order" message describes a rejected candidate swap; report its actual failed condition when available, without counting it as solved or inferring that every attempt failed for the same reason. If the user supplies a debug message that you cannot independently read, label it as user-reported evidence.

## Assign ownership

Identify the failing stage and owner from evidence, not where an error was logged. Self paid creation sent directly by the simulator to RPC happens before autopilot handles the order. Quote API errors may come from a solver or another provider. If ownership is unclear, say so.

Before calling an error unknown, investigate the original failure record. Join settling orders and errors by auction and solution, not just a shared auction or nearby timestamp. If submission records include a transaction signature, inspect the failed transaction and the first failing program in its logs; a later successful transaction does not identify the earlier failure. Use named program errors where available. A submission error wrapper does not mean the network or autopilot caused the failure.

Separate the confirmed failure from its underlying cause and repair owner. A verified Titan LessThanMinimumAmountOut confirms a minimum-output failure; Jupiter SlippageToleranceExceeded confirms a slippage-threshold failure whose input/output side must be checked from the instruction and amounts. Do not call every Jupiter 6001 a minimum-output failure. Compare the route's encoded allowance with the user's signed headroom before recommending wider swap slippage, and preserve both user limits. State the verified inequality clearly even if quote freshness, construction arithmetic or changes between simulation and execution still need investigation. Keep uncertainty about the repair owner separate from a confirmed swap mechanism; neither logging location nor the error name establishes a solver defect. Link failed transactions beside the affected orders and show when driver simulation passed before execution failed.

For solvers other than Jupiter, always produce 2 reports:

- `{timestamp}_{solverName}_solver_test_report.md`: solver performance, feature results, confirmed solver issues, accepted solver limitations and errors of unknown ownership. Keep unknown ownership errors in both reports with the same order evidence; label them **Ownership unknown**, not solver defects. Exclude errors confirmed to be unrelated to the solver. Keep brief test limitations needed to interpret the results, without unrelated service troubleshooting.
- `{timestamp}_{solverName}_solver_test_report_for_cow.md`: the complete report for the CoW team. Include solver results plus creation, quoting, services, RPC, settlement retries, cleanup and uncertain errors from the selected runs. Preserve all evidence and explanations, including those in the solver report.

Label the placed-order denominator and account for significant gaps from planned requests in both report summaries. Give grouped counts and brief test context in the solver report; keep full preplacement errors and CoW troubleshooting in the CoW report so missing orders cannot make an incomplete test look fully successful. Do not claim an autopilot defect without evidence of ownership.

Keep confirmed solver defects and limitations in the solver report, even if they surfaced through an API. Mark team-confirmed accepted solver limitations **known and accepted**; do not count them as unexpected failures or request an immediate fix. Restrictions enforced by autopilot or services belong only in the CoW report, including their error details and order links. Preserve the latest user-confirmed ownership rather than assuming an API rejection is a solver limitation. Shared settlement retries may still need solver input.

**Token-2022 transfer fees are an autopilot limitation.** Autopilot rejects these tokens before solver participation. Keep these rejections, error messages and related links only in the CoW report; do not describe them as a solver limitation or include them in the solver report.

Both reports must have an order table within every scenario, with a few successful examples and all failures in that report's scope. The solver report includes all confirmed solver failures and all errors of unknown ownership. A known failing stage does not by itself establish ownership; retain uncertain cases in both reports. The CoW report includes every failed placement, failed order and order with failed settlement attempts, including setup and cleanup. Group repeated attempts by order, retaining every distinct error and the final outcome. Check completeness against journals, order statuses and failure logs, not just the previous report. Missing failure evidence must be stated. Preserve existing rows and external links in the complete CoW report; repeat solver evidence there so it stands alone.

## Format

Use a neutral title such as "{Solver name} solver test report" for both reports. Do not state that a report is for the solver or the CoW team, and do not link the reports to each other. Keep their filenames and distinct content scopes.

Open with the date and environment, then **TLDR:** and 3–5 short sentences in simple, slightly informal English, like a quick message to a teammate. Start with a brief result and specific praise for what worked, supported by the run, then give the 1–2 biggest issues and useful first checks. Keep the visible reasoning short and put full diagnoses in the evidence blocks. Use everyday words and natural contractions. Explain technical terms when needed: "opposite orders did not match directly" is clearer than "CoW was not achieved". Give direct impacts such as orders never placed, trades left unfilled, extra retries or a feature not demonstrated. Use clear counts and distinguish planned trades from placed orders when the difference matters. If there were no major issues, say so and name the main test limit.

Explain why those issues happened when the evidence supports a cause. Clearly mark possible causes as unconfirmed. Say how they might be fixed, with an owner when known; when the cause is unknown, name the specific check needed before proposing a fix. Do not present a possible fix as proven or blame the solver for setup or service failures. Link each issue to representative affected orders, using a short label with tokens, amount, account mode or final outcome; use additional examples when they show a different pattern or outcome. Make clear if an attempt failed but the order later filled. Do not invent links for requests that failed before placement. Keep full errors and all affected orders in the scenario evidence; the TLDR should explain what matters without repeating that detail.

Keep the TLDR within each report's scope: solver issues and uncertain ownership in the solver report; service issues and unfinished cleanup may also appear in the CoW report. Follow with:

| Scenario         | Outcome                                                      | Next check                               |
| ---------------- | ------------------------------------------------------------ | ---------------------------------------- |
| 1. Scenario name | Goal achieved, not achieved or inconclusive; then fill count | 1 specific check, with owner where known |

Use a numbered section per scenario. Keep visible text to 2 short sentences: whether the goal was achieved, then the reason or impact. Keep setup details in the evidence block when they add length. Aim for 200-350 visible words for 5 scenarios, including the TLDR and summary table. Keep full CoW detail inside evidence blocks. Do not repeat the table or add separate Expected, Result and Impact paragraphs.

Put metrics, explanations, order evidence, transaction links and cleanup in 1 closed block per scenario:

```markdown
<details>
<summary>Order evidence and metrics</summary>

Total transactions: N. Median / longest fill: N / N seconds.

| Scenario row / trader | UTC timestamp        | Trade                                                                 | Error(s)                   | Debug tool URL                |
| --------------------- | -------------------- | --------------------------------------------------------------------- | -------------------------- | ----------------------------- |
| row / trader          | first failed attempt | Sell input amount SRC → DEST, or Buy SRC → exactly output amount DEST | exact error; final outcome | order link or why none exists |

</details>
```

Keep blank lines around Markdown inside the block. Do not use `open`. If the renderer cannot expand details, use short evidence subsections instead. Do not create a shared evidence appendix.

## Evidence and wording

- Include a few successful examples per scenario, chosen to show the tested feature or token types, plus all failures in scope. Preserve existing evidence when shortening. Keep exact amounts, decimals, input/output direction and final status. List every token whose sell or exact buy succeeded inside the token section; separate those lists. Use verified token symbols; retain mints in exact errors.
- Use the first failed-attempt timestamp for errors and placement time for successful examples; state this once. For cleanup without a scenario row, use `— / trader`. Use `### Cleanup failures (although orders were filled at later attempts)` only when verified. Keep cleanup collapsed unless it adds a separate actionable issue.
- Copy debug URLs from reports or the matching environment configuration. Quote failures have no order ID; failed creation UIDs may have no debug record. Label these cases and successful orders linked for context. Put transaction links beside the claims they prove. Local paths cannot replace shareable links.
- Use plain English and numerals for counts, durations, sizes and amounts. Keep confirmed causes separate from assumptions. Explain shared evidence gaps once; mark unavailable data as unavailable.
- Omit repeated prose, internal endpoints, long timelines, superseded configuration mistakes and instructions to search inaccessible logs. Include infrastructure or fee payer details only if needed to explain a finding.

## Compare with previous reports

When a previous report exists, add a short comparison to both new reports. Use the baseline named by the user, otherwise the latest earlier report for the same solver and environment. Match the solver and CoW report scopes separately. Use report dates and session metadata, not filenames alone; if no matching baseline exists, say so briefly. Ask only when the baseline choice is unclear.

Compare matching scenarios, planned and placed counts, fills, token sell and exact buy coverage, and meaningful changes in failures or timing. Keep denominators, expected-rejection exclusions, acquisition and cleanup exclusions, and timing endpoints consistent. If setup or evidence differs, explain the limit instead of calling the result an improvement or regression. Do not treat fewer placed orders or a different token mix as better solver performance.

After the scenario summary table, add `## Changes since {previous report date}` with 1 short numerical sentence and a closed `<details>` block titled `Comparison with the previous run`. Name the baseline briefly, then show only meaningful numerical changes in a compact before/after table. Summarize unchanged results in 1 line; avoid repeating the scenario explanations or adding a long comparison narrative.
